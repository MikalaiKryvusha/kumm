## 2. The pink-purple night — cause

`WorldTime.SetDayNightSceneLighting` changes only light INTENSITY (main 2.1 → 0.4, secondary 0.4 → 0.2) and
vignette (0 → 0.5). Colours were checked one by one and are NOT the cause:

- night lights `NightLight` (0.58, 0.38, 0.00), `NightLightingPoint` (0.55, 0.43, 0.17), `NightLighting`
  (0.60, 0.38, 0.17) — warm orange (`scan_night.py`, `scan_refs.py`);
- vignette colour in the profile — black (0, 0, 0, 1);
- ambient — Trilight grey (0.37) × 1.74, fog off.

The cause is the **static colour grading** of the camera's global volume — profile `FinalVersion5`
(`sharedassets1.assets` pathID 88873), its `ColorGrading` (pathID 88871). Decoded against the PPv2 field order
(`cg_words.py`; word index = 4-byte offset into the settings body after the name):

| Parameter | Override | Value | Effect |
|---|---|---|---|
| tonemapper | on | ACES | — |
| colorFilter | on | (1.00, 0.953, 0.873) | warm filter on everything |
| saturation | on | −10 | — |
| **lift** (shadows), words 68–72 | **on** | **(0.957, 0.827, 1.000) w +0.394** | shadows lifted and green-starved → **magenta** |
| **gamma** (midtones), words 73–77 | **on** | **(0.673, 0.725, 1.000) w −0.511** | midtones strongly **blue**, darker |
| gain (highlights), words 78–82 | on | (0.955, 0.998, 1.000) w −0.350 | near neutral |

By day the frame lives in highlights (neutral gain) and the warm colorFilter cancels the blue; at night
almost the whole frame is shadows + midtones, so magenta lift + blue gamma become the picture. `[AI]` This is
the strongest explanation found; it is not yet confirmed by an in-game before/after.

**Fix routes** (both reversible):
1. **In-place byte patch** of `sharedassets1.assets`: clear the override flags of lift/gamma/gain (words 68,
   73, 78 → 0) = PPv2 neutral defaults; or keep the brightness offsets and neutralise only the colour
   (xyz → 1, 1, 1). Same file size, three to nine words, backup first. Dies on a game update (re-run).
2. **BepInEx plugin** (Harmony postfix on `PostProcessingManager.Awake`): set the same parameters from code,
   with an ini to choose the variant. Survives updates unless the class changes; needs BepInEx installed.

## 3. Russian — how it works now and what "native" costs

Now: XUnity hooks every UGUI/TMP text, looks it up in `AutoTranslator/Translation/ru/Text/_AutoGeneratedTranslations.txt`
(7 982 lines, masterkosta's translation, 514 with `{{…}}` placeholders), font replaced by `rus_font`; a miss
goes to **DeepL online** (`Endpoint=DeepLTranslate`) — that is the visible "translation on the fly".

The game has **no localization system**: `Fluent.Language` is the dialogue asset's demo enum (English,
Spanish, Dutch… — no Russian) and strings are English literals in code and in scene/prefab data.

Where the dictionary's strings live (`dict_where.py` over the decompiled source):

| | Count |
|---|---|
| keys equal to a C# literal in `Assembly-CSharp` | 1 538 |
| keys inside a longer C# literal | 160 |
| keys not in code — scene/prefab/bundle text or composed at runtime | 6 284 |

Routes to "native":
- **A. Offline only (cheapest):** keep XUnity, set `Endpoint=` (empty) so nothing goes online; a missing
  line then stays English instead of a DeepL guess — removes the online part, not the hook.
- **B. Hybrid:** rewrite the 1 698 code literals in `Assembly-CSharp.dll` with Mono.Cecil from the dictionary
  (a re-runnable tool, like the rest of KUMM), keep XUnity for scene text and composed strings.
- **C. Fully native:** B + rewrite TMP/UGUI texts inside `level1`, `sharedassets*` and five Addressables
  bundles (5.8 GB) + bake a Cyrillic TMP font asset. Largest; every game update redoes the asset pass.
